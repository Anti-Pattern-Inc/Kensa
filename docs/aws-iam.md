# Permissions (IAM)

日本語: [ja/aws-iam.md](ja/aws-iam.md)

- **Policy**: the plugin creates no IAM resources (that would need IAM write permission, which contradicts "read-only"). **Any kind of profile works** (SSO, environment variables, assume-role, an instance role; boto3's standard lookup order). But **do not use a profile with administrator privileges** (with root-user credentials, commands such as `auth-check` and `scan-aws` stop; they pass only if you give `--allow-root`). The agent has a shell, so the profile's credentials can also be used by `aws` commands other than the scanner's code. The read-only block in the code protects only the paths that go through the scanner; the real boundary is IAM. If you already have a read-only role (for example `SecurityAudit`, meant for auditing), point `--profile` at it. If not, create one with the template below.
- **What kensa enforces, and what only IAM can**: `scan-aws` blocks write calls in code (list/describe/get only; secret-retrieval calls are blocked too), and `auth-check` / `scan-aws` refuse root-user credentials. kensa does **not** stop an administrator profile. `auth-check` makes a best-effort **admin check** (IAM list/get reads only) and prints a `warning:` when the principal's name suggests an administrator, when `AdministratorAccess` or `PowerUserAccess` is attached (to the role, the user, or the user's groups), or when an inline or customer-managed policy allows every action on every resource without a condition. It is a hint: it does not look at permission boundaries, SCPs or session policies, reads at most 10 policy documents, says `skipped` when IAM cannot be read (a narrow role usually cannot), and a quiet result is not proof of read-only. It only warns and never stops; the agent is told to stop and ask you. Commands the agent runs itself (the `aws` CLI in a shell, or `aws___run_script` of the optional IAM-authenticated MCP) are not covered by kensa's code guard. Whether an AWS session can write is decided by the profile's permissions, so give one read-only profile.
- **Split the profile in two**: a profile that reads the AWS environment (`aws.profile`; read-only) and a profile that touches the W-A Tool (`aws.wa_profile`; used by `seed --from-wa-tool` / `push` / `precheck` / `workload-create`). This keeps the write permission on the W-A Tool role alone and off the scan role. If `aws.wa_profile` is not set, `aws.profile` is used (you can also run without splitting). `--profile` always takes precedence. `auth-check` checks the scan side, and `auth-check --for wa` checks the W-A Tool side.
- **Template `iam/scan-role.yaml`** (CloudFormation): two roles, the scan role (`ReadOnlyAccess` + `SecurityAudit` + a Deny on reading values) and a W-A Tool write role that is created only when `CreateWaToolRole=true`. **Who can assume them** is restricted by `TrustedPrincipalArnPattern` (required). Read the contents first, then deploy it yourself (it needs `--capabilities CAPABILITY_NAMED_IAM`).
  ```bash
  aws cloudformation deploy --template-file iam/scan-role.yaml --stack-name kensa-roles \
    --capabilities CAPABILITY_NAMED_IAM --profile <a profile that can manage IAM> \
    --parameter-overrides TrustedPrincipalArnPattern='arn:aws:iam::123456789012:role/aws-reserved/sso.amazonaws.com/*AWSReservedSSO_PowerUserAccess_*' CreateWaToolRole=true
  aws cloudformation describe-stacks --stack-name kensa-roles --query 'Stacks[0].Outputs'   # prints the lines to paste into ~/.aws/config (ProfileSnippet)
  ```
  The pattern above trusts IAM Identity Center (SSO) users of one permission set. **If you sign in as an IAM user** (access keys in `~/.aws/credentials`), trust that user instead: `TrustedPrincipalArnPattern='arn:aws:iam::123456789012:user/<your-user-name>'` (or `…:user/*` for every IAM user of the account, which is broader). Get your ARN with `aws sts get-caller-identity --query Arn`. In the pasted profile, set `source_profile` to the profile that holds that user's keys.
  The Deny and the actions allowed for the W-A Tool are the same as the output of `iam-policy`, and a test pins that they match (so they cannot drift from the blocks in the code). `cfn-lint` passes (`uvx cfn-lint iam/scan-role.yaml`). **On one real account, deploy, assume-role, a scan, and recording with the W-A Tool role were verified. Not verified: that a principal outside the trust is refused (the denial case), and the case where `TrustedAccountId` names a different account** ([Verification status](verification.md)).
- **Scan role**: as before, `ReadOnlyAccess` + `SecurityAudit` (`references/aws-readonly-checks.md`). These are broad, so an **additional Deny that refuses known reads that return values or content** is attached (not exhaustive; see "What this Deny guarantees" below). `kensa.py iam-policy --kind scan-deny` prints the JSON (reads that return values or content: Secrets Manager, SSM parameters, S3 objects, Lambda configuration, ECR authorization tokens, CloudWatch Logs content, Athena query results, CloudFormation templates, CodeCommit blobs, EC2 console output, Redshift temporary credentials, and so on; plus reads of the data itself in DynamoDB and similar. API key values cannot be denied in IAM, because `apigateway:GET` covers every GET, so only the block in the code protects them).
- **What this Deny guarantees**: the list above is of **known** reads that return values or content. It is not a complete list of the data-fetching actions that `ReadOnlyAccess` and `SecurityAudit` allow. For example, `ReadOnlyAccess` allows `codecommit:Get*` and `codecommit:GitPull` (which return file contents) and `codebuild:BatchGet*` (build environment variables) (the AWS-managed policy, checked on 2026-11-02; `GetFile`, `GitPull` and `BatchGetBuilds` were added to the list). A read that is not on the list **can be run by another command that uses the same role** (the block in the scanner code protects only the APIs the scanner calls). If you must guarantee that values are never read, do not use the managed policies; replace them with your own policy that allows only the APIs the scanner calls (we do not publish such an allow-list, for the reason below).
- **For the W-A Tool**: `iam-policy --kind wa-tool-read` (fetching questions and reading reports) / `--kind wa-tool-write` (adds `UpdateAnswer`, `CreateWorkload` and `CreateMilestone`). A test pins that the allowed actions match the APIs the code calls. `Resource` is emitted as `*`, so narrow it to the workload ARN after you have confirmed the behavior in your own environment.
- **No allow-list (least privilege per API) is published.** The scanner calls dozens of APIs, and some API names differ from their IAM action names (for example, S3's `GetBucketEncryption` is `s3:GetEncryptionConfiguration`). We avoided calling something "least privilege" without being able to verify it offline. Narrow it down on a real account while watching for `denied`.
