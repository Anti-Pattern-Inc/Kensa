# 設計メモ

> 英語版が正本です: [docs/design.md](../design.md)

## 設計の要点

1. **証拠の経路を先に決める**: 各項目は、同梱の経路表(`assets/routing.json`)により `coverage` で次の3つに分かれる。標準レンズ(版 2025-02-25、307 項目)では、確定 226 / 下書き 40 / 面談のみ 41。
   - **確定**: AWS・リポジトリの証拠で判定できる(暗号化・ネットワーク防御・ログ/検知・シークレット・CI/テスト自動化など)。
   - **下書き**: 証拠は「ある」ことだけを言える(ポストモーテム・runbook・エスカレーション・脅威モデル・DR・ゲームデイ・振り返りなど。AWS の Incident Manager/Resilience Hub/FIS、GitHub の活動実績と文書が材料)。証拠は質問カードに事前入力され、**確認だけ**で済む。「見つからない」は ✗ の根拠にしない(別の場所にあるかもしれない)。
   - **面談のみ**: 文化・優先順位・経営の関与など、人にしか答えられない。AWS・リポジトリに現れない文書・定例・研修の有無も、ここに入る(Slack/Drive などの検索は行わず、質問カードで人に確認する)。
   証拠で触れる項目は 307 項目中 266(87%)。ただし「下書き」は人が確認するまで確定ではなく、OpenItems に出る。(分類は本プラグインの設計判断で、`assets/routing.json` が正本。)
2. **質問は項目ごとではなく「決定カード」で**: 面談が必要になりうる項目が **30 枚のカード**に集約される。カードに属さない項目は AWS/IaC だけで判定し、証拠が取れなければ仮置き(要確認)になる。各カードは「現状は ○/△/✗ のどれか」を選ぶだけ(検出済みの証拠が冒頭に出る)。4名程度の小さなチーム向けの**推奨(手順・工数・優先度・担当)と代替案(選ぶ条件・トレードオフ)**が付き、`{po}`・`{chat}`・`{vcs}` はチームのツールで埋まる。組織に合わせた変更は `.kensa/cards.local.json` で上書きする。
3. **事実を作らない**: 証跡も回答も無い項目は、○ にせず `✗ / 仮置き / 確信度L / 要確認` にする。自己申告の ○ は確信度 M 止まりで OpenItems に出る。AWS/リポジトリの強い証拠は、自己申告で上書きされない(下書きの経路は例外: 証拠は『ある』ことしか示さないので、人の回答が優先され、再スキャンでも上書きされない)。
4. **実環境優先**: IaC と実環境が食い違えば実環境を採用し、差異(ドリフトの疑い)を備考に残す。
5. **最新のレンズ**: `seed --from-wa-tool` が W-A Tool の `list_answers` から最新の質問・選択肢・改善計画 URL を取得する。レンズ更新時は同じコマンドの再実行で、既存の判定を保ったまま追加/削除項目を印付けする。
6. **一度で終わらせない(再レビュー)**: `snapshot` で判定を保存し、再スキャン後に `diff` で **悪化(○→△/✗)・改善・確認が進んだ項目・レンズの追加/削除・証拠が古い項目(既定 180 日)** を出す。項目ごとに証拠の記録時刻(`evidence_at`)を持ち、改善の期限と実施状態(`due` / `action_status`)も保存する。
7. **「未確認」と「未実施」を混ぜない**: 仮置き ✗ は未実施の確認ではない。Summary は **記録済み率**(判定が付いた割合)と **確認済み率**(仮置きも除いた割合)を分けて出し、`push` は仮置きの件数を警告して `--exclude-assumed` で送らずに済ませられる。判定の語彙は増やさない(W-A Tool には「未確認」の状態が無く、FTR に提出する値が崩れるため)。

## 汎用性(サンプルに依存しない)

| 問い | 答え |
|---|---|
| 全項目は MCP/API で取れるか | **取れる**。W-A Tool の `list_answers` が質問・選択肢・改善計画 URL を返す(`seed --from-wa-tool`)。ただし公式レンズは ExportLens で書き出せず(AWS提供のレンズは対象外と公式に明記)、ListAnswers は WorkloadId が必須。リソースも費用も発生しない一時的なワークロードを `workload-create` で作って取る。公式スキルは公式ドキュメントのページから質問・BP の一覧を作る(BP ID 単位)が、W-A Tool の ChoiceId は持たないので `push` には使えない。**ChoiceId まで機械的に取れるのはこの経路だけ**。AWS MCP Server から同じ API を呼んでも同じ。公式ドキュメントの検索(`aws___search_documentation`)は個別項目の補足用で、ChoiceId を持たない |
| 別のレンズ | `--lens <エイリアスまたは ARN>`。レンズごとに `--dir` を分ける |
| 経路表に無い項目(別レンズ・更新) | `route-unknown` が項目と語彙(areas・カード一覧)を JSON で出す → エージェントが分類 → `route-apply FILE` で `.kensa/routing.local.json` に登録(同梱の経路表は変えない)。末尾は必ず面談 |
| 組織ごとの推奨・カード | `.kensa/cards.local.json`(カード単位の上書きと追加) |
| CSV 取り込み | 列 Pillar / QuestionId / QuestionTitle / ChoiceId / BestPractice / Description(AWSCheckable は任意)があれば任意のシートを使える |

## IaC だけのモード(`mode iac`)

AWS の実環境を読めない・読まない場合(本番に触れない、権限が出ない、環境がまだ無い)の代替。`W mode iac`(`seed` の後)で切り替え、`W mode both` で戻す。`W mode` で現在の値を表示する。モードは worklist に保存され、再 seed でも残る。

| | `both`(既定) | `iac` |
|---|---|---|
| AWS の実環境 | `scan-aws`(37チェック) | **読まない**。`scan-aws` は止まり、`channel=aws` の判定も記録しない |
| IaC | `scan-repo`(種類・CI・文書・GitHub) | `scan-repo` に加えて **`scan-iac`**(Terraform・CloudFormation/SAM・`cdk synth` の出力を静的に読み、リソースの種類ごとに件数と設定のフラグを出す。AWS も認証も要らない) |
| 判定の確信度 | 設定値を直接確認 = H | IaC の宣言だけ = **M まで**(`apply` が、aws 経路を持つ項目の H を M に下げる) |
| 確認元の表示 | AWS(実環境)/ リポジトリ/IaC | aws 経路の項目を IaC で判定したものは **『IaC(実環境未確認)』**。OpenItems・Summary の注記・`status`・`push` の警告に出る |
| 面談カード | aws 経路の項目は `scan-aws` を待つ | `scan-iac` を待つ(aws は待たない) |

- **「IaC に無い」は ✗ の根拠にしない。** 手作業で作ったリソースも、別のスタック・リポジトリのリソースもある。見つからなければ判定せず、面談に回す。✗ / △ にするのは、IaC にあるのに設定が弱いと宣言されている場合だけ(解釈ルール: `references/iac-readonly-checks.md`)。
- 実環境を読めるようになったら `mode both` → `scan-aws`。実環境の判定(`channel=aws`)は IaC の判定より常に強く、`apply` すると置き換わり、印も消える。
- `scan-iac` は件数・フラグ・ファイル名だけを `.kensa/evidence/iac-scan.json` に出し、値(パスワードやキー)は保存しない。CDK のソース(`.ts` / `.py`)は読まないので、`cdk synth` の出力(`cdk.out/*.template.json`)を作ってから再スキャンする(スキャナーは synth を実行しない)。
- 公式スキル `aws-well-architected-review` も IaC を読む。このモードの違いは、全項目の網羅・面談カード・W-A Tool への記録・再レビューの差分が、IaC だけの場合も同じ流れで使えること。
