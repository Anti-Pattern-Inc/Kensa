# Known limitations

日本語: [ja/limitations.md](ja/limitations.md)

- The recommendations on the decision cards are examples that assume "4 people, GitHub, Slack, AWS (mostly containers)". For a different setup, override `recommend` / `alternatives` in `.kensa/cards.local.json` (`covers` is determined by `card` in `routing.json`).
- The classification of routes (AWS / repository / interview) is a design decision. Where it cannot be confirmed in the actual environment, it falls back to an interview.
- There is no feature that searches Slack, Drive and the like for evidence. For whether such documents or regular meetings exist, add `--evidence URL` to the answer of a decision card, or write it in the `evidence` of `apply`. To bring in verdicts alone in bulk you can also use the CSV import (`seed --from-csv --import-verdicts`), but the source then becomes "imported (needs re-check)", the confidence is Low, and the rationale is a fixed text.
- "Draft" evidence shows only **existence and activity**. A postmortem having been written does not mean it is good, and a busy channel does not mean escalation works. A person makes the final call.
- Culture, priorities and management involvement (41 interview-only items in the standard lens) cannot be filled from evidence.
- Even within `ReadOnly`, Organizations/SCP, billing and Cost Explorer may be visible only from the management account (they remain in OpenItems).
- The estimated HRI is a reference value. Questions that contain undetermined items or assumed (needs confirmation) items are counted as "verdict not final" and are left out of the HRI. The FTR verdict uses the values read back from the W-A Tool after `push --apply` (`precheck`).
- `seed --from-wa-tool` calls `ListAnswers` without a pillar filter, so the pillars of a lens that has its own pillars (or a pillar that a later lens adds) are fetched too, and take the name the W-A Tool gives them. This was checked against a real W-A Tool only for the standard lens; a custom lens with its own pillars has not been tried. The FTR scope (Security, Reliability, Operational Excellence) is fixed in the code.
- If a lens update adds new items to an already-answered card, `cards next` shows that card again. When you answer, all items of that card are overwritten with the same verdict (the earlier `--override` is not carried over). Answers recorded before `choice_ids` existed (old data) are still treated as answered per card, as before.
- **A workload that is not on the current lens version**: `seed` warns when `LensStatus` is not `CURRENT`, but it cannot fix it. Upgrading the lens review writes to the workload, so do it in the W-A Tool console and run `seed` again. On a real workload we have only seen `CURRENT`; the warning paths are tested with fakes and the botocore stubber.
- **How lens updates are matched**: items are matched by ChoiceId. If a lens update renames a ChoiceId, the old item is marked removed and the new one is added, so its verdict is not carried over (it stays on the removed item). A reworded item is flagged only when the old worklist came from the same source (a W-A Tool re-seed over a CSV is not compared, since the two word things differently), only the question, best practice and description are compared, and whitespace is ignored.
- **The bundled data is for one lens version**: the routing table, decision cards and evidence rules are written for lens version 2025-02-25 (307 items). Items that a later lens adds are not routed and go to interviews (`route-unknown`), so the share judged from evidence drops until the bundled data is updated. kensa has no automatic check that tells you the bundled data is out of date.
- "Evidence is stale" is the number of days since the **recorded time** (`evidence_at`), not since when the fact has been true. `diff` compares only against the point where a `snapshot` was taken (snapshots are not taken automatically).
- Editing the due date or action status of ActionPlan in the xlsx is not imported (a re-export restores them). Update them with `due` / `action_status` in `apply`. Importing edits made in xlsx/Sheets is not implemented.
- Importing the JSON output of the official skill (`aws-well-architected-review`) is not implemented. It will be built after PR #464 (https://github.com/aws/agent-toolkit-for-aws) is merged and the output schema is settled. Until then, map the official verdict vocabulary into `apply` following `status-mapping.md`.
- There is no mapping table for importing the suggestions of the AWS Well-Architected Agent (`status-mapping.md` is for the official skill). The Agent's output is in the form of suggestions, not a verdict per best practice, so if you use it, copy it into `apply` by hand as evidence.
- When the live environment is read through `aws___run_script` of the optional, IAM-authenticated AWS MCP Server, only IAM can make it read-only. The proxy's `--read-only` is a per-tool filter; how `readOnlyHint` is set was confirmed with an unauthenticated `tools/list` ([docs/aws-mcp.md](aws-mcp.md)), but whether the proxy actually hides them is not verified. Unlike the scanner (`scan-aws`), the MCP side has no mechanism that blocks writes in code. The bundled `aws-docs` is unauthenticated and does not touch the user's account.
- Running with Sheets as the source of truth (writing to Sheets directly and reading back) is not done. When you keep the file in Drive, the limit is uploading the xlsx.
- The verdicts of `mode iac` come only from reading the IaC **declarations**. Manual changes, other stacks and undeployed changes are invisible. Confidence stops at Medium, and the items stay in OpenItems as 'IaC (live environment not verified)'. Confirm in the live environment before submitting, for example, to the FTR.
- `scan-iac` is an approximation that reads files as strings. It does not handle CDK source, Pulumi, Terraform `count` / `for_each` / expansion through variables, a module called several times, or the output of `terraform plan`. Values passed through CloudFormation `!Ref` or parameters are counted as "not declared" (it errs toward the side that could not be confirmed). A flag is "the number of resources that declare that setting"; settings declared in a separate resource (such as S3 encryption) are merely added to the count, with no mapping to the resource they belong to. Port checks are an approximation that looks at nearby lines. Aurora specifies encryption and similar only on the cluster, so a simple comparison with the `rds` count does not match.
- There are only two modes, `both` and `iac`. There is no mode that reads only the live environment (if you do not want to read the repository, use `plan --skip repo`).
- **Artifact locales are `en` and `ja` only.** The Japanese cards (`assets/cards.ja.json`) are maintained separately from the English ones (`assets/cards.json`) and may drift. CLI messages, skills and references are in English, and the agent relays them in the user's language. For any other language, artifacts come out in English and the agent translates when it presents them. CSV / xlsx import accepts either the English column names (for example `Verdict`, `Org shape / tools`) or the older Japanese ones.

## Safety limitations

- **The scanner's guard (`ReadOnlyClient`) is an allow-list**: it lets through only list/describe/get calls, and blocks the known reads that return values, content or credentials (`DENY_RE`). It does not block every read API that the scanner does not call. The boundary is IAM.
- **The IAM Deny** is the list in `iam/scan-role.yaml` (`iam-policy --kind scan-deny`), an additional denial on top of the actions that `ReadOnlyAccess` / `SecurityAudit` contain, and it is **not exhaustive** (for example, `ReadOnlyAccess` allows `codecommit:GitPull` and `codebuild:BatchGet*`; actions that return content can remain beyond those added to the list. Details: [Permissions (IAM)](aws-iam.md)). `apigateway:GET` covers every GET and so cannot be denied; API key values are protected only by the block in the code (`get_api_keys`). The only denial confirmed to take effect on a real account is `ssm:GetParameter`. We have not checked how far `ReadOnlyAccess` / `SecurityAudit` currently include these actions (if they do not include one, the Deny is harmless).
- **The results fetched for Lambda (`lambda:ListFunctions`) and ECS (`ecs:DescribeTaskDefinition`) can contain environment variables.** Only counts and flags are stored, but the values do reach the scanner's memory. If you do not want them read, deny those APIs in IAM (some scanner checks will be lost).
- **`push --apply` overwrites existing answers and takes no snapshot beforehand.** `--milestone` is created after recording succeeds. For an already-answered workload, save a milestone in the W-A Tool first.
- **There is no mechanism that pins the target account of `--apply`.** The W-A Tool side is not checked against `aws.account_ids`. The user confirms the account that is displayed. A confirmation such as `--confirm-account` is not implemented.
- **`UpdateAnswer` / `CreateMilestone` of the W-A Tool role are `Resource: "*"` (all workloads).** A parameter to narrow them to a workload ARN is not implemented.
- **The trust policy** trusts the account root and narrows with a pattern on `aws:PrincipalArn`. If you make the pattern `arn:aws:iam::<account>:*` it opens to the whole account (`AllowedPattern` allows it). There is no MFA condition. The `aws-cn` / `aws-us-gov` partitions are not supported (`arn:aws:` only). `GLOBAL_REGION` (`us-east-1`) is also fixed.
- **What masking (`redact()`) covers is evidence, rationale, notes and similar** (`apply` and card answers). It is not applied to `na_reason`, `business answer --text`, `context set`, or the scan result files. It does not detect Bearer tokens, connection strings, or strings that are only a 40-character key. `--mask-account-ids` is off by default.
- The permissions of the state files are left at the default umask (not set to 0600). `scan-repo` follows symbolic links to files.
- `gh api` does not pass `--method GET` explicitly (the default of `gh api` is GET).
- **`gh skill install` installs only the skills.** `docs/`, `iam/` and `optional/` are not installed (get the IAM template from the repository). The documentation-search MCP (`aws-docs`) is bundled for Claude Code and is not installed this way; add the `mcpServers` of `mcp.json` yourself if you want it ([AWS MCP Server](aws-mcp.md)). When it is not connected, the flow opens `improvement_url` directly.
- Kiro: the skills ran on a real Kiro in one outside trial (v0.3.0); the v0.3.1 fixes, `optional/kiro-permissions.yaml` and the MCP connection have not been tried there yet ([Verification status](verification.md)). Kiro shows only skills, not the Claude Code commands: use `/kensa-demo`, `/kensa-review`, `/kensa-resume` and `/kensa-partner-record`.
- `precheck` checks that the workload **name** contains the solution name (only when `--solution-name` is given). AWS also accepts the solution name in the workload description, which `precheck` does not check.
